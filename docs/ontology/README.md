# TOR Checker Ontology

`tor-checker.owl` is an OWL 2 ontology of the whole TOR Checker application. It covers:

- **Users:** roles, accounts and access levels.
- **Data model:** every MongoDB entity, its fields and the allowed values of each enum.
- **Behaviour:** features, API endpoints and frontend pages.
- **Pipeline:** how a TOR travels through ingestion and the AI pipeline.
- **Deployment:** where each part runs.

Every fact is taken from the code on `main`.

### Rules the ontology enforces

Cardinality restrictions record the rules of the data model:

- A user account has exactly one role. A `VendorUser` has the vendor role and an `AdminUser` the admin role.
- A vendor profile belongs to exactly one vendor, and a vendor has at most one profile (`ownsProfile` is functional both ways).
- A bookmark links exactly one vendor profile and one TOR, and has exactly one application status.
- A TOR has exactly one pipeline status and one display status. Its fairness flags are only `FairnessFlag`s, and each flag belongs to exactly one TOR.
- An enrichment job enriches exactly one TOR, and a TOR has at most one job.
- A user has at most one chat conversation.
- Each endpoint belongs to exactly one router and needs exactly one access level.

### The pipeline

```text
Discovery (BMA e-GP) ──┐                      ┌─> Lifecycle refresh ──> Bid deadline extraction
                       ├─> AI enrichment ─────┤
Capture (national e-GP)┘    └ fairness signals └─> Match notification (SendGrid)
  └ keyword gate, PDF inspection

Stalled-run detection runs on its own and alerts admins.
```

Each stage records:
- the Cloud Run job or service that runs it;
- the external service it reads or calls;
- the collections it writes;
- the source folder that implements it.

### Example data

A few individuals named `Example_*` show how real records fit together:
- a vendor and their profile;
- an enriched, open TOR with a procurement record, a bid deadline, an AI summary and one fairness flag;
- a bookmark of that TOR;
- a match result for the vendor and the TOR.

Each one is marked "Illustrative example data, not a real record." The reasoner classifies the example TOR as a `PubliclyListedTor`, a `FlaggedTor` and an `OpenForBidsTor`.

**Match score weights:** category 40 · technology stack 35 · budget range 25 (total 100).

### Example query

Which features can a vendor use, and through which endpoints?

```sparql
PREFIX tor:  <https://github.com/SW-Process/TOR_website/ontology#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?feature ?endpoint WHERE {
  ?f tor:availableTo tor:VendorRole ; rdfs:label ?feature ; tor:realizedBy/rdfs:label ?endpoint .
  FILTER(lang(?feature) = "en")
}
ORDER BY ?feature ?endpoint
```

Run it in Protégé (*Window → Tabs → SPARQL Query*) or with `rdflib`.

## Opening it in Protégé

1. *File → Open* → `docs/ontology/tor-checker.owl`.
2. *Reasoner → HermiT → Start reasoner*. No class turns red, and the defined classes above get their members.
3. Browse *Entities*. For example:
   - `TOR` shows the restrictions on a TOR;
   - `F_Bookmarks` shows its role, pages, endpoints, collections and code;
   - `Stage_Enrichment` shows its place in the pipeline.
4. Labels are in English and, where the UI has one, Thai. Choose the language under *View → Render by label (rdfs:label)*.

## Keeping it current

Don't edit the `.owl` file by hand; it is generated.

1. Change the facts in `build_ontology.py`. For example:
   - add a row to `ENDPOINTS` when you add a route;
   - add a value to an `enum(...)` call when you add a Mongoose enum value;
   - add an entry to `FEATURES` or `PAGES`.
2. Regenerate:
   ```sh
   pip install rdflib
   python docs/ontology/build_ontology.py docs/ontology/tor-checker.owl
   ```
3. Run the reasoner in Protégé, re-run `sparql_examples.py`, and update the numbers above.
